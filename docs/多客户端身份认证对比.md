# 多客户端身份认证对比与企业架构建议

> 回答三个问题：
> 1. 其他 MCP 客户端（ChatGPT / Claude）也是这样开发的吗？
> 2. 它们的自定义 MCP 能否获取**实际用户的授权**？
> 3. 企业构建 MCP 服务给全员使用，怎么分清楚请求是谁来的？

**核心结论：这不是 WorkBuddy 的缺陷，而是 MCP 协议的统一设计。
所有客户端都遵循同一套标准；「能不能识别到人」取决于用哪种认证方式，而不是用哪个客户端。**

---

## 一、MCP 规范怎么规定的（权威依据）

来自 `modelcontextprotocol.io/specification/.../basic/authorization`：

> Authorization is **OPTIONAL** for MCP implementations. When supported:
> - Implementations using an **HTTP-based transport SHOULD conform to this specification**
> - Implementations using an **STDIO transport SHOULD NOT follow this specification,
>   and instead retrieve credentials from the environment**
> - Implementations using alternative transports MUST follow established security best practices

规范同时定义了两种授权类型，**正好对应两类场景**：

| Grant Type | 适用场景（规范原文） |
|---|---|
| **Authorization Code** | "useful when the client is acting on behalf of a **(human) end user**. For instance, an agent calls an MCP tool implemented by a SaaS system." |
| **Client Credentials** | "the client is another application (**not a human**). For instance, an agent calls a secure MCP tool to check inventory… **No need to impersonate the end user.**" |

### 这解释了一切：先分清你的服务是哪一类

| | stdio（本地进程） | 远程 HTTP / SSE |
|---|---|---|
| 进程模型 | 每个客户端一个子进程 | 长期运行、共享服务 |
| 身份 | **继承启动它的 OS 用户** | **每请求携带 bearer token** |
| 凭证来源 | 环境变量（规范明确规定） | OAuth 2.1 资源服务器 |
| 租户模型 | **单用户、单一信任域** | **多租户** |
| 网络面 | 无（管道） | HTTPS 端点 |
| 适用 | 本地开发工具、个人包装 | **企业内部平台、SaaS** |

**你的场景（企业系统给全员提供 MCP）属于右列 → 必须 OAuth。**

## 二、三大客户端对比（实测/官方文档）

### Claude

官方文档 `claude.com/docs/connectors/building/authentication` 列出 6 种认证类型：

| 类型 | 说明 | 可用性 |
|---|---|---|
| `oauth_dcr` | OAuth 2.0 + 动态客户端注册（RFC 7591） | 开箱支持 |
| `oauth_cimd` | OAuth 2.0 + Client ID Metadata Document | 开箱支持 |
| `oauth_anthropic_creds` | OAuth 2.0 + Anthropic 持有客户端凭证 | 需联系审批 |
| `custom_connection` | 连接时输入自定义 URL / 凭证 | 需联系审批 |
| `static_headers` | **固定凭证（API Key / Bearer）** | Beta |
| `none` | 无认证 | 支持 |

**关键原文（OAuth 模式下每人独立登录）：**
> **OAuth 2.0**: each user signs in to your service with **their own account** when they connect

**关键原文（静态凭证是共享的，不能识别人）—— 这段几乎是写给本项目的：**
> **Treat it as the organization's credential, not a person's**: every member's requests
> carry the same key, so **don't use it to identify which user is calling**.
> If your tools need to act as the individual user, **use OAuth instead**.

**不支持机器对机器：**
> A machine-to-machine `client_credentials` grant isn't supported, and
> Anthropic-held client credentials are the consent-gated alternative.

> A pure machine-to-machine `client_credentials` grant, where a token is issued
> with no user in the loop, **isn't supported**.

其他硬性要求：必须 PKCE `S256`；`401` 是触发登录的前提（忽略 200 上的 `WWW-Authenticate`）；
只取元数据 `authorization_servers` 列表的**第一个**；发现/注册/令牌端点 **10 秒**超时。

### ChatGPT (OpenAI)

官方文档 `platform.openai.com/docs/guides/developer-mode`：

> Supported MCP protocols: **SSE and streaming HTTP**.
> **Authentication supported: OAuth, No Authentication, and Mixed Authentication**
> For OAuth, **if static credentials are provided, then they will be used.**
> Otherwise, ChatGPT can use Client ID Metadata Documents… ChatGPT can also use DCR.

创建 app 时：
> Provide the endpoint and required metadata for your MCP server.
> Pick the authentication mechanism, if applicable.
> Click Scan Tools and wait for the scan to complete.
> **If your server uses OAuth, complete the authorization prompt**, then wait for the tool scan to finish.

**所以 ChatGPT 同样支持每用户 OAuth 授权。**

### WorkBuddy

| 场景 | 机制 | 能否识别到人 |
|---|---|---|
| 连接器包 `auth_mode` 省略 | 标准 MCP OAuth，需授权时开浏览器 | ✅ |
| 连接器包 `auth_mode: server-side` / `gateway` | 云端托管 OAuth | ✅ |
| 连接器包 `auth_mode: token` | 弹表单填凭证 | ⚠️ 取决于凭证是否每人不同 |
| 裸 `~/.workbuddy/mcp.json` + `headers` | 静态凭证 / 环境变量 | ❌ 共享，无法识别到人 |

### 汇总对比

| 能力 | WorkBuddy | Claude | ChatGPT |
|---|---|---|---|
| OAuth（每人独立登录） | ✅ | ✅ | ✅ |
| 静态凭证（**组织共享**） | ✅ | ✅ | ✅ |
| 无认证 | ✅ | ✅ | ✅ |
| 纯 M2M `client_credentials` | — | ❌ 明确不支持 | — |
| **静态凭证能识别到人？** | ❌ | ❌（官方明确警告） | ❌ |

**这是行业共识，不是某家的实现问题。**

## 三、直接回答你的顾虑

> 「我得实现我的系统 MCP 服务能够分清楚请求是谁过来的吧，不然我如何提供服务呢 不乱套了」

**完全正确，而且这正是标准要解决的问题。** 关键在于选对认证方式：

### ❌ 会导致「乱套」的做法

用**静态共享凭证**（一个 API Key 给全公司用）：

```
全公司 → 同一个 token → 你的 MCP 服务
```

后果：服务端只知道"这是本公司的人"，**不知道是张三还是李四** →
无法做数据隔离、无法审计、无法按人授权。Claude 官方把这点称为
"don't use it to identify which user is calling"。

### ✅ 正确的做法：MCP 服务做 OAuth 2.1 资源服务器

```
员工 A ──┐
员工 B ──┼─→ WorkBuddy / Claude / ChatGPT（OAuth 客户端）
员工 C ──┘         │  每人各自授权，拿到自己的 token
                   ▼
            你的 MCP 服务（OAuth 2.1 资源服务器）
                   │  验证 token → 解析出「当前是谁」
                   │  按身份返回各自的数据
                   ▼
            企业统一认证中心（OAuth 授权服务器）
                   │  员工用企业账号登录
                   ▼
              你的业务系统（按 userId 隔离数据）
```

**职责划分：**

| 角色 | 由谁承担 | 职责 |
|---|---|---|
| OAuth 客户端 | WorkBuddy / Claude / ChatGPT | 发起授权、存 token、每请求带上 |
| **OAuth 资源服务器** | **你的 MCP 服务** | 只**验证** token、解析用户身份 |
| OAuth 授权服务器 | **企业统一认证中心**（SSO） | **签发** token、管账号生命周期 |

**你的 MCP 服务不需要自己实现认证中心**，只需：
1. 对未认证请求返回 `401` + `WWW-Authenticate`（带 `resource_metadata`）
2. 提供 `/.well-known/oauth-protected-resource`，声明 `authorization_servers` 指向企业 SSO
3. 验证 SSO 签发的 JWT，从 claims 里取 `sub` / `email` 等作为用户标识

这样：**员工开户/离职/权限复核继续由企业既有体系管，MCP 服务只管"认人"。**

## 四、为什么你的自定义 MCP 现在拿不到身份

回顾本项目实测结论（详见 `docs/多用户身份识别方案.md`、`docs/连接器授权机制.md`）：

| 环节 | 现状 | 结果 |
|---|---|---|
| 传输方式 | HTTPS/SSE 远程服务 | 属"应遵循 OAuth"的一类 |
| 服务端对未认证请求 | 直接放通（`permitAll`） | **从不返回 401 → 客户端永不触发 OAuth** |
| 客户端配置 | 裸 `mcp.json`，无 `auth_mode` 声明 | 被当作"无需认证的服务" |
| 凭证 | 静态写在 `headers` | 组织共享，无法识别人 |

**根因：401 是整个 OAuth 流程的触发器。你从不返回 401，客户端就认为无需认证。**

（本项目已内置该能力，`workbuddy.oauth.challenge-enabled=true` 即可开启。）

## 五、企业落地的三个层次

### 层次 1：内部小范围，快速验证
每个员工在自己机器的 `mcp.json` 里配**各自的** token。
- ✅ 能识别人、无需审核
- ❌ 靠人工分发，token 轮换麻烦

### 层次 2：正式产品（推荐）
打包成连接器包，实现 OAuth 2.1 资源服务器，`auth_mode` 走 OAuth。
- ✅ 每人用企业账号授权一次
- ✅ 支持吊销、审计、按人授权
- ⚠️ 需要企业有 OAuth 授权服务器（SSO / Keycloak / Entra ID 等）

### 层次 3：CLI 方案（已有成熟 CLI 时）
如果企业系统已有命令行工具，用 CLI + Skill 方案，由 CLI 自管登录态
（WorkBuddy 的 `cli.json` 支持 `auth` / `status` / `unAuth`，还支持 OAuth Device Flow）。
- ✅ 跨平台、凭证与安装目录分离
- ❌ 需要维护 CLI

## 六、一句话总结

| 你的疑问 | 答案 |
|---|---|
| 其他客户端也是这样吗？ | 是。MCP 规范统一规定，Claude / ChatGPT 都实现了 OAuth 客户端侧 |
| ChatGPT / Claude 能拿到真实用户授权吗？ | **能**。OAuth 模式下每位用户用自己的账号登录（Claude 原文：each user signs in with their own account） |
| 静态凭证能识别人吗？ | **不能**。Claude 官方明确警告"don't use it to identify which user is calling" |
| 企业该怎么做？ | 远程 MCP 服务实现 **OAuth 2.1 资源服务器**，授权服务器指向企业 SSO，每用户独立 token |
| 会乱套吗？ | 用 OAuth 就不会。用共享 API Key 一定会 |
| 要自建认证中心吗？ | 不用。对接企业已有的 SSO 即可，你的服务只做"验证 + 解析人" |

**判断口诀：**

> 本地 stdio → 单用户，环境变量，不用 OAuth
> 远程 HTTP → 多租户，**必须 OAuth**，401 是触发器
> 要识别到具体的人 → **只能 OAuth**，静态凭证永远做不到
