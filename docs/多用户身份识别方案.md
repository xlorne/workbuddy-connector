# 多用户场景：MCP 服务如何识别「当前访问人」

> 结论先行：**WorkBuddy 直连自定义 MCP（裸 `mcp.json`）时不会传递任何用户身份。
> 多用户身份识别必须走「连接器（Connector）」渠道的 OAuth / Token 认证模式。**

本文所有结论均基于本机实测 + WorkBuddy 开放平台官方文档，实验过程可复现。

---

## 一、实测证据：为什么你现在拿不到身份

### 证据 1：172 次真实调用的请求头里没有任何用户标识

服务端抓包统计（WorkBuddy 5.8.2 真实发起）：

```
POST /mcp/message   × 110   (工具调用)
GET  /sse           ×  78   (连接握手)

携带 Authorization 的请求数 : 0
携带任何身份 header 的请求数 : 0
```

110 次工具调用出现过的**全部**请求头：

| 请求头 | 次数 | 是否含用户身份 |
|---|---|---|
| `host` / `connection` / `content-type` / `accept` / `accept-encoding` | 110 | 否 |
| `user-agent`（`WorkBuddy/5.8.2`） | 110 | 否 |
| `mcp-protocol-version` | 104 | 否 |
| `caller_method` | 80 | 否 |
| `traceparent`（W3C 链路追踪） | 80 | 否 |
| `x-model-id` | 10 | 否 |

**结论：一条用户身份信息都没有。**

### 证据 2：调用 `whoami` 工具的实际返回

```
authenticated : false
userId        : null
tokenPresent  : false
identityHeaders : {}
```

### 证据 3：401 挑战实验 —— WorkBuddy 不会自动做 OAuth 发现

我按 MCP 规范给 `/sse` 加了标准 401 挑战：

```
HTTP/1.1 401
WWW-Authenticate: Bearer realm="workbuddy-connector",
                  resource_metadata="http://localhost:3100/.well-known/oauth-protected-resource"
```

结果（服务端日志实测）：

| 行为 | 次数 |
|---|---|
| `GET /sse` → 401（WorkBuddy 发起） | **40** |
| `GET /.well-known/oauth-protected-resource`（WorkBuddy 发起） | **0** |

WorkBuddy 只是**无限重连**，从未去读 `WWW-Authenticate` 里给出的发现地址。

> 那 1 次发现请求经核实 UA 为 `curl/8.7.1`，是我自己的验证请求，不是 WorkBuddy。

### 证据 4：WorkBuddy 确实会给「内置连接器」注入上下文，但不含用户身份

环境变量 `CODEBUDDY_MCP_CONFIG` 显示，内置连接器经由本地代理（`127.0.0.1:64947`）接入，
并注入两个头：

```
Authorization: Bearer <50 字符>              # 会话凭证，非用户身份
X-WorkBuddy-MCP-Context: <746 字符，Base64>  # 解出来是：
```

`X-WorkBuddy-MCP-Context` 解码后：

```json
{
  "sessionId": "aabc5a51-...",
  "welcomeMode": "working",
  "workspace": "/Users/lorne/developer/git-workspace/java/workbuddy-connector",
  "allowedBuiltinTools": ["automation_update", "..."]
}
```

**注意：只有 sessionId / workspace，没有任何用户标识。** 而且这套机制**不作用于**用户自定义的 MCP。

## 二、官方机制：MCP OAuth 2.1（`open.workbuddy.cn/docs/connector`）

WorkBuddy 官方把身份识别能力定义在**「连接器」**体系中，共四种认证场景：

| 场景 | 接入方式 | 是否打开浏览器 |
|---|---|---|
| MCP Server 自带 OAuth 或无需认证 | `auth_mode` 省略，按标准 MCP 流程连接 | 需授权时打开 |
| WorkBuddy 云端托管 OAuth | `auth_mode: server-side` 或 `gateway` | 需授权时打开 |
| **用户自行填写 Access Token / API Key** | **`auth_mode: "token"` + `token-schema.json`** | 不打开 |
| CLI 登录 | `cli.json` 的 `auth` / `status` / `unAuth` | 取决于 CLI |

### OAuth 流程（拿到「具体是谁」的正规路径）

WorkBuddy 内置 OAuth 管理器自动完成客户端侧流程，**OAuth 2.1 + PKCE，以公共客户端身份接入**（不持有 `client_secret`）：

```
首次请求未携带 Token
      ↓ 返回 401 + WWW-Authenticate
发现元数据  /.well-known/oauth-protected-resource
      ↓
动态客户端注册  POST /oauth/register        (RFC 7591)
      ↓
打开浏览器授权  GET  /oauth/authorize       (PKCE S256)
      ↓ 用户用【企业账号】登录
校验 state 并交换 Token  POST /oauth/token
      ↓
携带 Bearer Token 正常调用   ← 此时服务端才知道「是谁」
```

**服务端需要实现的端点：**

| 端点 | 方法 | 作用 |
|---|---|---|
| `/.well-known/oauth-protected-resource` | GET | 返回 `resource` 与 `authorization_servers` 列表 |
| `/.well-known/oauth-authorization-server` | GET | 授权服务器元数据（正式环境由企业 SSO 提供） |
| `/oauth/register` | POST | 动态客户端注册，须回显 `redirect_uris` |
| `/oauth/authorize` | GET | 授权端点，须支持 `code_challenge_method=S256` |
| `/oauth/token` | POST | 校验 `code_verifier`，签发 access/refresh token |

**关键约束：**

- 必须支持 PKCE（`S256`），授权码一次性、有效期约 10 分钟
- 回调优先用 WorkBuddy 私有协议：
  `workbuddy://workbuddy/mcp/connector%3A<source>/oauth/callback`
  被拒绝时可回退到 `http://127.0.0.1:{动态端口}/oauth/callback`
- `access_token` 建议 1 小时，`refresh_token` 建议 ≥30 天；过期自动续期
- 所有 OAuth 端点强制 HTTPS

### 用户自填 Token 模式（无需自建 OAuth 服务器）

服务不提供 OAuth、只有 PAT / API Key 时使用。用户点「连接」后弹表单填凭证，
**凭证仅存本机、不经云端、不打开浏览器**。

需要 `auth_mode: "token"` + `token-schema.json`，且 `mcp.json` 里的 `${VAR}` 占位符
必须与表单字段 `key` **完全一致（区分大小写）**：

```json
{
  "mcpServers": {
    "your-service": {
      "type": "streamableHttp",
      "url": "https://api.example.com/mcp",
      "headers": { "Authorization": "Bearer ${API_KEY}" }
    }
  }
}
```

## 三、根因：为什么现在的配置拿不到身份

| 环节 | 现状 | 是否满足身份识别 |
|---|---|---|
| `auth_mode` 声明 | **没有 `connector-meta.json`**，是裸 `mcp.json` | ❌ |
| 服务端 401 挑战 | 现在是 `permitAll`，从不返回 401 | ❌ |
| WorkBuddy OAuth 发现 | 即使返回 401 也不触发 | ❌ |
| 静态 headers | 只能放**一个固定值**，代表「配置」不代表「人」 | ❌ |

**核心矛盾**：`mcp.json` 的 `headers` / `env` 是**静态配置**——
一份配置对应一个固定值。它天然无法表达「这是张三还是李四」。

官方对连接器有明确要求：
> 涉及用户数据时必须提供认证鉴权，并遵循最小权限原则。

也就是说，**身份识别是「连接器」级别的能力，不是裸 MCP 配置能实现的**。

## 四、方案对比

| 方案 | 能识别到具体人 | 用户操作 | 是否需审核上架 | 适用场景 |
|---|---|---|---|---|
| A. 静态 headers（裸 `mcp.json`） | ❌ 所有人共用一个 token | 无 | 否 | 服务账号、单用户工具 |
| B. 每人各自配自己的 token | ✅ | 每人配一次 | 否 | 小团队、内部快速落地 |
| C. 连接器 + `auth_mode: token` | ✅ | 每人填一次凭证 | ✅ 需提交审核 | 有 PAT/API Key 的服务 |
| D. 连接器 + `auth_mode: server-side`（OAuth） | ✅ **且对接企业 SSO** | 每人授权一次 | ✅ 需提交审核 | **企业统一认证（推荐）** |

### 方案 B：每人各自配 token（最快落地，无需审核）

让用户在自己的 `~/.workbuddy/mcp.json` 里填**属于自己的** token：

```json
{
  "mcpServers": {
    "schedule": {
      "type": "sse",
      "url": "http://localhost:3100/sse",
      "headers": {
        "Authorization": "Bearer ${USER_TOKEN}"
      }
    }
  }
}
```

服务端按 token 反查用户即可识别访问人。
**缺点**：用户量大了难以管理；token 轮换麻烦；无法强制失效。

### 方案 D：连接器 + OAuth（企业推荐，正确做法）

架构上把职责拆开：

```
WorkBuddy（OAuth 客户端）
      │  401 挑战 → 发现 → PKCE 授权
      ▼
你的 MCP 服务（OAuth 资源服务器）  ←─ 只验证 token，不签发
      │  authorization_servers 指向
      ▼
企业统一认证中心（OAuth 授权服务器）  ←─ 用户用企业账号登录，签发用户 token
```

**MCP 服务只做资源服务器**，身份治理（开户 / 销户 / 权限复核）继续由企业既有体系负责。
这正是你想要的「企业统一认证登录人标识」。

## 五、本服务已提供的实现

代码位置：`src/main/java/com/workbuddy/connector/oauth/`

| 文件 | 作用 |
|---|---|
| `OAuthDiscoveryController` | `/.well-known/oauth-protected-resource` 与 `oauth-authorization-server` 两个发现端点 |
| `OAuthChallengeEntryPoint` | 返回 401 + `WWW-Authenticate`，触发客户端授权流程 |
| `CallerIdentityResolver` | 验签后从 JWT claims 提取登录人标识 |

### 如何启用

```yaml
workbuddy:
  oauth:
    challenge-enabled: true                                   # 开启资源服务器模式
    resource: http://localhost:3100                           # 本服务规范地址
    authorization-servers:
      - https://sso.your-company.com                          # 【关键】企业统一认证中心

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://sso.your-company.com            # 用于验签企业签发的 token
```

或用命令行临时开启（便于实验）：

```bash
java -jar target/workbuddy-connector-1.0.0.jar \
  --workbuddy.oauth.challenge-enabled=true \
  "--workbuddy.oauth.authorization-servers[0]=https://sso.your-company.com"
```

### 实测验证（已通过）

开启后服务端行为：

```
$ curl -i http://localhost:3100/sse
HTTP/1.1 401
WWW-Authenticate: Bearer realm="workbuddy-connector",
                  resource_metadata="http://localhost:3100/.well-known/oauth-protected-resource"

$ curl http://localhost:3100/.well-known/oauth-protected-resource
{
  "resource": "http://localhost:3100",
  "authorization_servers": ["https://sso.example-company.com"],
  "scopes_supported": ["openid", "profile"],
  "bearer_methods_supported": ["header"]
}
```

端点行为完全符合 RFC 9728 + MCP 规范。

> ⚠️ **注意**：如本文第一节实验所示，**裸 `mcp.json` 的 WorkBuddy 客户端不会消费这个 401**。
> 要真正走通 OAuth，需要把服务按「连接器」规范打包
> （`connector-meta.json` + `mcp.json` + `icon.svg`）**提交 WorkBuddy 团队审核上架**。
> 届时 `connector-meta.json` 中声明 `auth_mode`。

## 六、推荐落地路径

```
第 1 步  短期可用（今天就能做）
        方案 B：让每个用户在各自 mcp.json 里填自己的 token
        → 服务端按 token 识别用户，立刻验证多用户隔离逻辑

第 2 步  正式产品化（推荐）
        把服务打包成「连接器」，声明 auth_mode
        ├─ auth_mode: "token"        → 服务已有 PAT/API Key 体系时用
        └─ auth_mode: "server-side"  → 对接企业统一认证中心（OAuth 2.1）
        提交 WorkBuddy 团队审核，进入连接器市场

第 3 步  服务端改造
        当前代码已具备资源服务器能力，只需：
        ① 配置 authorization-servers 指向企业 SSO
        ② 配置 issuer-uri 以验签
        ③ 收敛 identity-headers 候选列表（生产环境不可信任客户端自带头）
```

## 七、生产环境安全提醒

1. **`challenge-enabled` 开启后，`/__capture/**` 仍公开**——这是为联调保留的观测端点，
   生产环境必须移除或加认证。
2. **不要信任客户端自带的身份 header**（`X-WB-User-Id` 等）。
   一旦走 OAuth，应只信任**已验签 JWT** 的 claims，把 `identity-headers` 候选列表清空。
3. `mcp.json` 中**不得写入真实凭证**，只能用 `${VAR}` 占位符（官方硬性要求）。
