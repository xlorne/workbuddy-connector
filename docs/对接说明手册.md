# WorkBuddy Connector 对接说明手册

> 版本 1.0.0 ｜ 适用 WorkBuddy 5.8.x ｜ 最后更新 2026-10-16

本文面向**接入方与运维**：如何把这个 MCP 服务接进 WorkBuddy、如何确认身份透传是否生效、出问题怎么查。

面向开发者的架构与实现细节，见 [`技术开发说明.md`](./技术开发说明.md)。

---

## 一、这个服务是做什么的

一句话：**验证「WorkBuddy 调用 MCP 时，服务端能不能知道是谁在调用」。**

它同时是一份**可运行的身份透传参考实现**：

- 作为 **MCP 服务**，向 WorkBuddy 暴露 7 个工具；
- 作为 **OAuth 2.1 资源服务器**，能让 WorkBuddy 走标准授权流程拿到「用户绑定的 token」；
- 内置**全链路抓包**与**身份探针**，不需要翻日志就能看清服务端收到了什么。

### 你能用它回答的问题

| 问题 | 用哪个能力 |
|---|---|
| WorkBuddy 调用时到底传了什么参数？ | `echo_call_context` 工具 / `/__capture/requests` 端点 |
| 服务端识别到我是谁？ | `whoami` 工具 / `/__capture/whoami` 端点 |
| 为什么识别不到用户？ | `list_captured_requests` 看请求头 |
| 怎么让服务端识别到人？ | 见第四章「两种身份对接方式」 |

## 二、快速开始

### 环境要求

| 项 | 要求 |
|---|---|
| JDK | 17 及以上 |
| Maven | 3.8+ |
| 端口 | **3100**（固定，勿改，详见 FAQ Q1） |

### 构建与启动

```bash
# 构建
mvn clean package

# 启动（前台）
java -jar target/workbuddy-connector-1.0.0.jar

# 或用脚本启动（后台，日志在 /tmp/workbuddy-connector.log）
./scripts/start.sh -d
```

启动成功标志：

```
Tomcat started on port 3100 (http) with context path '/'
OAuth 资源服务器模式已启用
 使用内置授权服务器（仅本地联调）
```

### 30 秒自检

```bash
# 健康检查（应返回 status=UP 及各模式开关）
curl http://localhost:3100/__capture/health

# 未认证访问 MCP 端点（应返回 401 + WWW-Authenticate）
curl -i -X POST http://localhost:3100/mcp
```

> **注意**：本机 curl 若走了 `http_proxy` 环境变量，访问 127.0.0.1 会失败。
> 请加 `--noproxy '*'`，例如 `curl --noproxy '*' http://localhost:3100/__capture/health`。

### 完整链路验证（推荐）

```bash
python3 scripts/verify_oauth_flow.py   # 8 步 OAuth 授权全链路
python3 scripts/verify_mcp.py          # MCP 协议握手 + 工具调用
```

`verify_oauth_flow.py` 期望输出（节选）：

```
[1] POST /mcp（未携带 token）→ 状态码 : 401
[4] POST /oauth/register     → 状态码 : 201
[5] GET  /oauth/authorize    → 登录页 : 已返回 HTML 表单
[6] POST /oauth/login        → 状态码 : 302
[7] POST /oauth/token        → 状态码 : 200
[8] POST /mcp（Bearer token）→ 登录人标识 : zhangsan / 姓名 : 张三 / claims验签 : True
```

## 三、WorkBuddy 侧配置

配置文件：`~/.workbuddy/mcp.json`（用户级）。

### 推荐配置（OAuth 模式）

```json
{
  "mcpServers": {
    "workbuddy-connector": {
      "type": "streamableHttp",
      "url": "http://localhost:3100/mcp"
    }
  }
}
```

**要点：**

- `type` 必须是 **`streamableHttp`**（不是 `sse`）。OAuth 授权链路依赖 Streamable HTTP。
- **不要配置 `headers`**。用户 token 由 OAuth 流程动态注入，写死 headers 反而会退化成「共享身份」。

### 配置生效方式

> ⚠️ **WorkBuddy 不会自动重载 `mcp.json`。** 修改后必须：
> - **重启 WorkBuddy**，或
> - 在「连接器管理」里把该 MCP 的**开关关掉再打开**

实测依据：改配置并重启服务端后，服务端捕获到的客户端请求数为 **0**，工具调用报
`sse_session_not_found`（客户端仍在用缓存的旧会话）。

### 备选配置（静态凭证模式）

不启用 OAuth 时，可用固定请求头（**注意：这是共享身份，无法区分具体用户**）：

```json
{
  "mcpServers": {
    "workbuddy-connector": {
      "type": "sse",
      "url": "http://localhost:3100/sse",
      "headers": { "X-WB-User-Id": "zhangsan" }
    }
  }
}
```

> 服务端需同时把 `workbuddy.oauth.challenge-enabled` 设为 `false`，并把
> `spring.ai.mcp.server.protocol` 改回 `SSE`。

## 四、两种身份对接方式

### 方式 A：OAuth 2.1（推荐，能识别到具体的人）

**用户视角的体验：**

1. 首次连接时，WorkBuddy 收到 `401` → 自动发现授权服务器
2. **弹出授权登录页**（本地联调用内置页，测试账号见下方）
3. 登录成功后，WorkBuddy 拿到 `access_token` 并加密存于本机
4. 后续每次调用自动携带该 token，服务端即可识别登录人

**本地联调测试账号**（`application.yml` 的 `workbuddy.oauth.demo-users`）：

| 账号 | 密码 |
|---|---|
| `zhangsan` | `123456` |
| `lisi` | `123456` |
| `wangwu` | `123456` |

**涉及的服务端端点：**

| 端点 | 方法 | 作用 |
|---|---|---|
| `/mcp` | POST | MCP 端点；无 token 时返回 401 + 挑战 |
| `/.well-known/oauth-protected-resource/mcp` | GET | 受保护资源元数据（RFC 9728） |
| `/.well-known/oauth-authorization-server` | GET | 授权服务器元数据（RFC 8414） |
| `/oauth/register` | POST | 动态客户端注册（RFC 7591） |
| `/oauth/authorize` | GET | 授权端点，返回登录页 |
| `/oauth/login` | POST | 登录并签发一次性授权码 |
| `/oauth/token` | POST | 校验 PKCE，签发 access / refresh token |

### 方式 B：静态请求头（简单，但识别不到具体的人）

服务端对所有人识别出同一个 `userId`。仅适用于**服务账号**或**单人调试**。

> 行业共识：静态凭证是「组织的凭证」，不是「某个人的凭证」。
> Claude 官方文档原话：*"Treat it as the organization's credential, not a person's…
> don't use it to identify which user is calling."*

## 五、Token 生命周期与自动续期

> 常见疑问：**access_token 是 JWT，有时效，那 token 过期后请求不是又 401 了吗？**

**答案是：会 401 —— 这是设计如此，但用户感知不到。** 关键在于 `refresh_token`。

### 4.1 两个令牌的分工

| 令牌 | 有效期 | 作用 | 存放 |
|---|---|---|---|
| `access_token` | **短期**（默认 1 小时） | 每次调用携带，证明「我是谁」 | 内存 / 客户端 |
| `refresh_token` | **长期**（默认 30 天） | access_token 过期时**静默换新** | 加密存于客户端本机 |

**为什么 access_token 要短**：它每次请求都在网络上传输，泄露风险最高。
有效期越短，被窃取后可利用的窗口越小。这是 OAuth 的标准实践。

### 4.2 过期后的完整时序（已实测）

```
用户正常使用
   │
   ├─ access_token 有效 ────────────────→ 200 正常返回
   │
   ├─ access_token 过期（如 1 小时后）
   │     │
   │     ├─ 服务端返回 401 + WWW-Authenticate
   │     │
   │     └─ 客户端【自动】用 refresh_token 换取新 access_token
   │           （WorkBuddy 内置 OAuth 管理器完成，用户无感知）
   │
   └─ 用新 access_token 重试原请求 ────→ 200 正常返回
```

**整个过程用户看不到任何弹窗**，除非 `refresh_token` 也失效（超过 30 天未使用），
此时才会重新要求授权登录。

### 4.3 实测结果

运行 `python3 scripts/verify_token_refresh.py`（需配合短 TTL 启动，见脚本注释）：

```
[2] 有效 token 调用            → 200，识别到 zhangsan
[4] 过期 token 调用            → 401  ✓ 过期被正确拒绝
[5] refresh_token 换新 token   → 200，且令牌已轮换
[6] 新 token 调用              → 200，仍正常识别身份  ← 业务无感
[7] 重放旧 refresh_token       → 400（已作废）        ← 防重放
```

### 4.4 安全机制

| 机制 | 说明 |
|---|---|
| **令牌轮换** | refresh_token **一次性使用**，换新后旧令牌立即作废 |
| 客户端绑定 | refresh_token 绑定发起的 `client_id`，防止被其他客户端盗用 |
| 有效期限制 | refresh_token 有 30 天有效期，超期需重新授权 |
| 过期清理 | 服务端定期清理过期令牌，并有容量上限防内存增长 |

### 4.5 时钟容差（重要排查点）

JWT 时间戳校验默认带 **60 秒时钟容差**，用于容忍客户端/服务端时钟漂移。

**这意味着**：token 过期后 60 秒内，服务端仍可能判定为有效。
如果你在测试「过期 → 401」时发现没有立刻 401，**先检查这个容差**，
可临时设置 `workbuddy.oauth.clock-skew-seconds: 0` 精确验证。

### 4.6 相关配置

```yaml
workbuddy:
  oauth:
    access-token-ttl-seconds: 3600   # access_token 有效期
    refresh-token-ttl-days: 30       # refresh_token 有效期
    max-refresh-tokens: 1000         # 刷新令牌容量上限
    clock-skew-seconds: 60           # 时钟容差（测试过期行为时设 0）
```

## 六、MCP 工具清单

WorkBuddy 可直接调用以下工具（共 7 个）：

| 工具名 | 用途 | 关键参数 |
|---|---|---|
| **`whoami`** | **最常用**。返回服务端识别到的登录人身份 | 无 |
| `echo_call_context` | 回显本次调用的参数 + HTTP 方法/路径 + 全部请求头 | `label`（可选） |
| `list_captured_requests` | 列出最近捕获的请求快照 | `limit`（默认 20，上限 100） |
| `last_request_headers` | 最近一次请求的完整请求头与请求体（不截断） | 无 |
| `list_my_schedule` | 按服务端身份隔离的日程示例，并做身份一致性校验 | `date`、`claimedUser` |
| `ping` | 最简健康检查（不触碰任何上下文，用于 A/B 对照） | 无 |

### `whoami` 返回结构

```json
{
  "authenticated": true,
  "userId": "zhangsan",
  "userIdSource": "jwt.claim.sub",
  "displayName": "张三",
  "tenantId": "example-corp",
  "scopes": ["openid", "profile"],
  "tokenPresent": true,
  "claimsVerified": true,
  "claims": { "sub": "zhangsan", "name": "张三", "...": "..." },
  "identityHeaders": { "x-wb-user-id": "zhangsan" },
  "summary": "认证状态: 已认证\n登录人标识: zhangsan\n..."
}
```

### 字段含义

| 字段 | 说明 | 关注点 |
|---|---|---|
| `userId` | **服务端认定的登录人标识** | 这是最终结论 |
| `userIdSource` | 标识来源 | `jwt.claim.sub` = 来自 token；`header.*` = 来自请求头 |
| `claimsVerified` | claims 是否来自**已验签**的 token | **`false` 时不可作为鉴权依据** |
| `authenticated` | 是否通过认证 | `false` 表示匿名调用 |
| `identityHeaders` | 命中的身份类请求头 | 用于确认企业网关实际注入了哪些头 |

> ⚠️ **重要**：`userIdSource` 以 `header.` 开头且 `claimsVerified=false` 时，
> 说明身份来自**客户端可伪造的请求头**，只能用于观测，不能用于生产鉴权。

## 七、观测端点（REST，免登录）

不经过 MCP 协议，浏览器或 curl 直接访问：

| 端点 | 说明 |
|---|---|
| `GET /__capture/health` | 健康检查 + 当前协议与 OAuth 开关 |
| `GET /__capture/whoami` | 本次请求解析出的身份 |
| `GET /__capture/requests?limit=20` | 最近请求列表 |
| `GET /__capture/requests/{id}` | 某次请求的完整细节 |
| `DELETE /__capture/requests` | 清空抓包缓冲（开始新一轮联调） |

示例：

```bash
# 看当前身份
curl --noproxy '*' http://localhost:3100/__capture/whoami

# 带身份头，观察服务端如何解析
curl --noproxy '*' http://localhost:3100/__capture/whoami \
     -H "Authorization: Bearer <你的JWT>" \
     -H "X-WB-User-Id: zhangsan"
```

> **安全提示**：`/__capture/**` 端点为联调方便而**免登录开放**。
> **生产环境必须移除或加认证**，否则会泄露请求头（可能含 token）。

## 九、常见问题排查

### Q1：服务启动后端口不是 3100？

**原因**：WorkBuddy IDE 会向子进程注入 `SERVER__PORT` 环境变量（IDE 自身端口，如 50430）。
Spring Boot 的 relaxed binding 会把它当作 `server.port`，**环境变量优先级高于 `application.yml`**。

**已解决**：启动类以「命令行参数」方式注入端口（命令行参数优先级高于环境变量）。

**如需改端口**：

```bash
# 方式一：启动时加参数
java -jar target/workbuddy-connector-1.0.0.jar --server.port=3200

# 方式二：设置环境变量
WORKBUDDY_CONNECTOR_PORT=3200 java -jar target/workbuddy-connector-1.0.0.jar
```

### Q2：改了 `mcp.json` 但不生效

**必须重启 WorkBuddy**（或关闭再打开连接器开关）。WorkBuddy 不监听配置文件变化。

### Q3：工具调用报 `sse_session_not_found`

客户端仍在使用**旧的 SSE 会话**。说明 `mcp.json` 已被改成 `streamableHttp` 但客户端未重载。
→ 重启 WorkBuddy。

### Q4：连接后没弹授权页

依次检查：

1. `mcp.json` 的 `type` 是否为 `streamableHttp`
2. 服务端 `challenge-enabled` 是否为 `true`
3. 直接验证：`curl -i -X POST http://localhost:3100/mcp` 是否返回 401
4. 检查服务端日志有没有收到请求（客户端可能根本没重连）

### Q5：`claimsVerified` 是 `false`

说明 token 未通过验签，服务端只做了 Base64 解码。

**原因**：未配置 `spring.security.oauth2.resourceserver.jwt.issuer-uri`，
或使用的是本地内置授权服务器（对称密钥，需 `embedded: true`）。

### Q6：curl 访问 localhost 失败

本机 `http_proxy` 环境变量导致。加 `--noproxy '*'`。

### Q7：MCP 工具调用超时/无响应

检查 Tomcat 线程数。SSE 长连接会独占线程，默认已配 `max: 200`。
若客户端保持大量连接，可适当调大 `server.tomcat.threads.max`。

### Q8：用了一段时间后突然 401，是配置坏了吗？

不是。**这是 access_token 到期了**，属正常行为。客户端应用 `refresh_token` 自动换新后重试，
用户无感知。详见第五章「Token 生命周期与自动续期」。

若**持续** 401 且无法恢复，检查：

1. `refresh_token` 是否也已过期（默认 30 天）→ 需重新授权
2. 服务端是否重启过（内置授权服务器的令牌存在**内存**中，重启即失效）
3. `/oauth/token` 的刷新请求是否返回 200（看服务端日志 `[OAUTH-AS] 刷新令牌成功`）

### Q9：测试「token 过期 → 401」时没有立刻复现

JWT 校验默认有 **60 秒时钟容差**。设 `workbuddy.oauth.clock-skew-seconds: 0`
并把 `access-token-ttl-seconds` 调小（如 8）即可精确复现。详见第五章 5.5 节。

## 十、上线前检查清单

### 必须完成

- [ ] `workbuddy.oauth.embedded` 改为 `false`，改用企业统一认证中心
- [ ] `workbuddy.oauth.authorization-servers` 填入企业 SSO 地址
- [ ] 配置 `spring.security.oauth2.resourceserver.jwt.issuer-uri`（用于验签企业 token）
- [ ] 删除 `workbuddy.oauth.demo-users` 演示账号
- [ ] **关闭或加固 `/__capture/**` 观测端点**（当前免登录）
- [ ] 收敛 `workbuddy.identity.identity-headers` 候选列表至企业实际使用的字段
- [ ] 确认所有流量走 HTTPS（远程 MCP 必须 HTTPS）
- [ ] 业务系统侧仍要按 `userId` 做数据权限过滤（OAuth 只解决「你是谁」）

### 建议完成

- [ ] 抓包缓冲容量按需调整（`workbuddy.capture.max-records`，默认 200）
- [ ] 日志级别与脱敏策略确认（避免 token 落日志）
- [ ] 多实例部署时，OAuth 状态改存 Redis/DB
- [ ] 加入调用审计日志

## 十一、附：完整配置参考

```yaml
server:
  port: 3100
  address: 127.0.0.1
  tomcat:
    threads:
      max: 200          # SSE/长连接需较大线程数
      min-spare: 20

spring:
  ai:
    mcp:
      server:
        name: workbuddy-connector
        version: 1.0.0
        protocol: STREAMABLE          # OAuth 链路要求
        streamable-http:
          mcp-endpoint: /mcp
        capabilities:
          tool: true
          resource: true
          prompt: true

workbuddy:
  server:
    port: 3100

  oauth:
    challenge-enabled: true           # true=OAuth 资源服务器模式
    resource: http://localhost:3100/mcp
    resource-path: /mcp
    embedded: true                    # true=内置授权服务器（仅联调）
    embedded-issuer: http://localhost:3100
    demo-users:                       # 生产环境删除
      zhangsan: "123456"
    authorization-servers: []         # 生产：企业 SSO 地址
    scopes-supported: [openid, profile]
    realm: workbuddy-connector

  capture:
    enabled: true                     # 抓包过滤器开关
    max-records: 200
    max-body-chars: 8000

  identity:
    mask-token: false
    identity-headers:                 # 身份 header 候选（生产应收敛）
      - x-wb-user-id
      - x-wb-corpuserid
      - x-wecom-userid
    user-id-claims:                   # userId 从 claims 提取的顺序
      - sub
      - user_name
      - preferred_username
      - email
```
