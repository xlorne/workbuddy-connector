## 一、项目定位与设计目标

这不是一个业务系统，而是一个**观测与参考实现**，要回答一个具体问题：

> WorkBuddy 调用远程 MCP 时，服务端能不能知道「是谁在调用」？如果不能，怎么才能？

由此推导出三条设计目标：

| 目标 | 实现手段 |
|---|---|
| **看得见** —— 无须翻日志就知道客户端传了什么 | 全链路抓包过滤器 + 身份探针工具 |
| **说得清** —— 明确区分「可信身份」与「仅供参考」 | 分层身份解析 + 可信度标注 |
| **可落地** —— 提供能直接复用的正确做法 | 完整 OAuth 2.1 资源服务器实现 |

### 2.2 过滤器链顺序

顺序至关重要，决定了「鉴权失败时能否留痕」：

```
HTTP 请求
  │
  ├─ ① RequestCaptureFilter          @Order(HIGHEST_PRECEDENCE)
  │     进入即记录 → 即使后续 401 也留痕
  │
  ├─ ② CallerContextFilter           绑定 HttpServletRequest 到 ThreadLocal
  │
  ├─ ③ PermissiveJwtAuthenticationFilter
  │     验签成功 → 写入 JwtAuthenticationToken
  │     验签失败 → 仅告警，不拦截（观测模式）
  │
  ├─ ④ Spring Security 授权链
  │     challenge-enabled=true  → /mcp 未认证则 401
  │     challenge-enabled=false → 全部放通
  │
  └─ ⑤ MCP 传输层
        Streamable HTTP: /mcp
        OAuth 端点:      /.well-known/**  /oauth/**
        观测端点:        /__capture/**
```

### 2.3 一次工具调用的完整链路

```
WorkBuddy
  │  POST /mcp  (JSON-RPC tools/call)
  ▼
[RequestCaptureFilter]  记录请求快照
  │
[PermissiveJwtAuthenticationFilter]  有 Bearer → 验签 → SecurityContext
  │
[SecurityConfig]  challenge-enabled 时校验是否已认证
  │
[MCP Streamable HTTP]  路由到工具方法
  │
[CallerIdentityResolver]
  │  ① SecurityContext 有 JwtAuthenticationToken → claimsVerified=true
  │  ② 否则解码 JWT payload         → claimsVerified=false
  │  ③ 否则读身份 header            → claimsVerified=false
  │  ④ 都没有                       → 匿名
  ▼
工具方法拿到 CallerIdentity → 按 userId 返回/过滤数据
```

## 四、核心组件详解

### 4.1 传输层：为什么必须用 Streamable HTTP

`McpServerProperties.ServerProtocol` 有三个取值：`SSE`、`STREAMABLE`、`STATELESS`。

**实测结论（重要）**：

| 传输 | `/mcp` 端点 | OAuth 授权链 |
|---|---|---|
| SSE | `/sse` + `/mcp/message` | ❌ 服务端返回 401 后，客户端**不发起** OAuth 发现 |
| **Streamable HTTP** | `/mcp` | ✅ 401 → 发现 → 注册 → 授权 → 换 token |

因此 `protocol: STREAMABLE` 是 OAuth 链路的前置条件。

> **注意**：Spring AI 的自动配置按 `protocol` 互斥装配，
> 一个应用实例只能选一种传输。

### 4.2 安全层：双模式设计

`SecurityConfig` 依据 `workbuddy.oauth.challenge-enabled` 切换：

**观测模式（false，默认）**

```java
http.authorizeHttpRequests(auth -> auth.anyRequest().permitAll());
```

目的：本地还没有企业 token 时也能连上，先看清客户端传了什么。

**资源服务器模式（true）**

```java
http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/.well-known/**").permitAll()   // 发现端点必须公开
        .requestMatchers("/oauth/**").permitAll()         // 授权端点必须公开
        .requestMatchers("/__capture/**").permitAll()     // 观测端点（生产应关闭）
        .requestMatchers("/mcp", "/mcp/**", "/sse", "/mcp/message").authenticated()
        .anyRequest().permitAll())
    .exceptionHandling(ex -> ex.authenticationEntryPoint(entryPoint));
```

**关键点**：发现端点与授权端点**必须公开** —— 一个被登录保护的发现文档毫无意义。

#### PermissiveJwtAuthenticationFilter 的取舍

标准资源服务器在 token 无效时直接 401。本服务刻意放宽：

- **已配 `issuer-uri`** → 正常验签，成功写入 `JwtAuthenticationToken`
- **未配 `issuer-uri`** → 跳过验签，但**不拦截**，身份解析自动降级并标注 `claimsVerified=false`

> ⚠️ **踩坑记录**：本过滤器必须写入 `JwtAuthenticationToken`。
> 早期版本写入 `UsernamePasswordAuthenticationToken`，导致
> `CallerIdentityResolver` 的 `instanceof JwtAuthenticationToken` 判定失败，
> **出现「验签日志打印成功、但 claimsVerified 却是 false」的矛盾现象**。

### 4.3 身份解析：分层策略（核心）

`CallerIdentityResolver` 按**信任度从高到低**判定登录人：

| 优先级 | 来源 | `authenticated` | `claimsVerified` | 可否用于鉴权 |
|---|---|---|---|---|
| 1 | Spring Security 已验签 JWT | `true` | `true` | ✅ 可以 |
| 2 | 未验签解码的 JWT | `true` | `false` | ❌ 仅观测 |
| 3 | 身份 header（网关注入） | `false` | `false` | ❌ 仅观测 |
| 4 | 无 | `false` | `false` | — |

**判定逻辑（简化）**：

```java
// ① 已验签
if (auth instanceof JwtAuthenticationToken jwtAuth) {
    return fromVerifiedJwt(jwtAuth.getToken());   // claimsVerified = true
}
// ② 未验签解码（仅观测）
if (token != null) {
    Map<String,Object> claims = decodeJwtPayloadUnverified(token);
    if (!claims.isEmpty()) return buildFromClaims(claims);  // claimsVerified = false
}
// ③ 身份 header
if (!identityHeaders.isEmpty()) return fromHeader();
// ④ 匿名
return CallerIdentity.anonymous();
```

**字段提取规则**：

- `userId`：按 `workbuddy.identity.user-id-claims` 顺序在 claims 中首个非空值
  （默认 `sub` → `user_name` → `preferred_username` → `userid` → `email`）
- `displayName`：`name` → `real_name` → `nickname` → `display_name` → `userId`
- `tenantId`：`tenant_id` → `corp_id` → `corpid` → `org_id`
- `scopes`：解析 `scope`（支持字符串空格/逗号分隔，或数组）或 `scp`

**设计要点**：`userIdSource` 字段始终记录命中来源，
联调时能立刻确认企业走的是哪条链路，不需要猜。

### 4.4 抓包：RequestCaptureFilter

**关键设计决策：请求进入时立即记录，而非放在 `finally`。**

```java
// ✅ 正确做法
recordOnEntry(request);                  // 进入即记录（请求头已完整）
if (isStreamingRequest(request)) {       // Accept: text/event-stream
    filterChain.doFilter(request, response);   // 不包 ContentCachingRequestWrapper
    return;
}
ContentCachingRequestWrapper wrapped = new ContentCachingRequestWrapper(request);
filterChain.doFilter(wrapped, response);
recordBody(wrapped);                     // 普通请求结束后补记 body
```

**为什么不能放 `finally`**：SSE 是长连接，`finally` 要等客户端断开才执行，
导致「握手请求迟迟抓不到」，联调时误判为没抓到包。

**为什么流式请求不能包 wrapper**：包装器会尝试缓存响应体，破坏长连接的流式输出。

存储为环形缓冲（`RequestCaptureStore`，默认 200 条），
提供 `recent(n)` / `latest()` / `clear()`。

### 4.5 OAuth 2.1：三个组件的分工

#### ① OAuthChallengeEntryPoint —— 一切的起点

```java
String metadataUrl = origin + "/.well-known/oauth-protected-resource" + properties.getResourcePath();
String challenge = String.format("Bearer realm=\"%s\", resource_metadata=\"%s\"", realm, metadataUrl);
response.setStatus(401);
response.setHeader("WWW-Authenticate", challenge);
```

**这是整个链路的触发器**：服务端不返回它，客户端就认为「无需认证」，
永远不会带上「当前用户是谁」的凭证。

**路径拼接遵循 RFC 9728 §3.1**：资源标识符含路径时，
元数据地址为 `{origin}/.well-known/oauth-protected-resource{资源路径}`。

#### ② OAuthDiscoveryController —— 让客户端知道去哪授权

```java
@GetMapping(value = {
        "/.well-known/oauth-protected-resource",          // 兼容无后缀
        "/.well-known/oauth-protected-resource/mcp"       // 规范要求（带资源路径）
}, produces = MediaType.APPLICATION_JSON_VALUE)
```

返回：

```json
{
  "resource": "http://localhost:3100/mcp",
  "authorization_servers": ["http://localhost:3100"],
  "scopes_supported": ["openid", "profile"],
  "bearer_methods_supported": ["header"]
}
```

**双路径提供的原因**：客户端实现存在差异。
已知 Claude Code 存在「只查无后缀路径」的问题（`/.well-known/oauth-protected-resource` 返回 404 即放弃）。
同时提供两条路径可最大化兼容性。

#### ③ EmbeddedOAuthAuthorizationServer —— 内置授权服务器（仅联调）

实现四个端点：

| 端点 | 安全要点 |
|---|---|
| `POST /oauth/register` | 返回 `201`，**必须回显 `redirect_uris`**（否则客户端无法继续） |
| `GET /oauth/authorize` | **回调地址与注册值精确匹配**，防止开放重定向 |
| `POST /oauth/login` | 生成**一次性**授权码（10 分钟有效），`state` 原样回传 |
| `POST /oauth/token` | 校验 PKCE `S256`；授权码 **`remove` 即消费**，防重放 |

**PKCE 校验实现**：

```java
byte[] digest = MessageDigest.getInstance("SHA-256")
        .digest(codeVerifier.getBytes(StandardCharsets.US_ASCII));
String computed = Base64.getUrlEncoder().withoutPadding().encodeToString(digest);
return computed.equals(codeChallenge);
```

**JWT 签发**：HMAC-SHA256，claims 含 `iss`/`sub`/`aud`/`exp`/`scope` 及演示用员工档案。

> **生产环境必须关闭本实现**（`embedded: false`），改为对接企业 SSO。
> 本服务只做**资源服务器**：验证 token、解析身份，不签发 token。

### 4.6 工具层

`ToolProviderConfig` 统一注册：

```java
@Bean
public ToolCallbackProvider identityTools(IdentityInspectorTools a, ScheduleTools b, PingTools c) {
    return MethodToolCallbackProvider.builder()
            .toolObjects(a, b, c)
            .build();
}
```

**设计考量**：

- 工具命名**直白**（`whoami`、`echo_call_context`），让模型在不确定时能主动调用并回显真实内容
- `ScheduleTools` 把身份**写进业务返回值**，验证身份能否真正驱动业务逻辑，而不只是打印
- `PingTools` 提供**最小对照工具**（不触碰任何上下文），用于隔离排查：若 ping 正常而 whoami 挂起，问题在上下文而非传输层

### 4.7 启动类：端口保护

```java
private static String[] withPortDefaults(String[] args) {
    // 命令行参数优先级 > 环境变量
    if (!hasPort) merged.add("--server.port=" + port);
    if (!hasAddress) merged.add("--server.address=127.0.0.1");
}
```

**解决的问题**：WorkBuddy IDE 向子进程注入 `SERVER__PORT`（IDE 自身端口），
Spring Boot relaxed binding 会当作 `server.port`，而**环境变量优先级高于 `application.yml`**，
导致服务静默监听错误端口。

**为什么不用 `System.clearProperty`**：环境变量走独立的
`systemEnvironment` 属性源，清 System property 无效。
**命令行参数的属性源优先级高于环境变量**，才是正确解法。

## 五、关键设计决策汇总

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 传输协议 | Streamable HTTP | OAuth 授权链的必要条件 | 放弃 SSE 兼容 |
| 安全模式 | 双模式开关 | 联调期先能连上，再收紧 | 需明确告知不可直接上生产 |
| JWT 验签 | 宽容（验签失败不拦截） | 观测优先，标注重可信度 | 宽松模式不可用于生产鉴权 |
| 抓包记录时机 | 请求进入即记录 | SSE 长连接下 finally 延迟严重 | 普通请求的 body 需二次补记 |
| 身份解析 | 分层 + 来源标注 | 让联调结论可解释 | 调用方需理解 `claimsVerified` |
| 授权服务器 | 内置 + 可切换企业 SSO | 本地可完整验证，生产可对接 | 内置实现需明确禁用 |

## 六、扩展指南

### 6.1 接入企业统一认证中心

**第一步：配置企业 SSO**

```yaml
workbuddy:
  oauth:
    challenge-enabled: true
    embedded: false                                    # 关闭内置授权服务器
    resource: https://mcp.your-company.com/mcp         # 公网 HTTPS 地址
    resource-path: /mcp
    authorization-servers:
      - https://sso.your-company.com                   # 企业 SSO

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://sso.your-company.com     # 自动拉取 JWKS 验签
```

**第二步：确认企业 SSO 支持以下能力**

| 端点 | 要求 |
|---|---|
| `/.well-known/oauth-authorization-server` | 返回 issuer 与各端点 |
| `/oauth/register` | 支持动态客户端注册（或提供固定 client_id） |
| `/oauth/authorize` | 支持 `code_challenge_method=S256` |
| `/oauth/token` | 校验 `code_verifier`，支持 `refresh_token` |

**第三步：回调地址**

WorkBuddy 优先使用私有协议回调：

```
workbuddy://workbuddy/mcp/connector%3A<source>/oauth/callback
```

被拒时回退到 `http://127.0.0.1:{动态端口}/oauth/callback`。
企业 SSO 需把这两类都加入白名单。

### 6.2 新增一个 MCP 工具

```java
@Component
public class MyTools {
    private final CallerIdentityResolver resolver;

    public MyTools(CallerIdentityResolver resolver) { this.resolver = resolver; }

    @Tool(name = "my_tool", description = "清晰描述何时使用此工具")
    public Map<String, Object> myTool(
            @ToolParam(description = "参数说明", required = false) String param) {
        CallerIdentity me = resolver.resolve();
        // 用 me.userId() 做数据隔离
        return Map.of("userId", me.userId());
    }
}
```

然后加入 `ToolProviderConfig` 的 `toolObjects(...)`。

> **注意**：`@Tool` 的 `description` 直接决定模型是否会正确调用，
> 必须写清「做什么、什么时候用」。

### 6.3 收敛身份字段（上线前必做）

```yaml
workbuddy:
  identity:
    identity-headers:      # 只保留企业网关实际注入的字段
      - x-your-gateway-user-id
    user-id-claims:        # 按企业 token 实际 claim 名调整
      - sub
      - employee_no
```

## 七、验证与测试

### 7.1 端到端脚本

| 脚本 | 覆盖范围 |
|---|---|
| `scripts/verify_oauth_flow.py` | 完整 OAuth 2.1 链路（8 步） |
| `scripts/verify_mcp.py` | MCP 协议握手 + 工具调用 |

**为什么必须用原始 socket**：SSE / 分块流响应会被 `urllib`、`http.client` 缓冲，
以及 `curl -N` 重定向到文件时也会缓冲，导致「服务端已应答但客户端读不到」的假象。
脚本因此直接操作 socket 逐行解析。

### 7.2 OAuth 链路 8 步

```
[1] POST /mcp 未带 token          → 401 + WWW-Authenticate
[2] GET  /.well-known/oauth-protected-resource/mcp → 200
[3] GET  /.well-known/oauth-authorization-server   → 200
[4] POST /oauth/register          → 201
[5] GET  /oauth/authorize         → 200（登录页）
[6] POST /oauth/login             → 302（带 code + state）
[7] POST /oauth/token             → 200（PKCE 校验通过，签发 JWT）
[8] POST /mcp  (Bearer)           → 200（服务端识别出 userId）
```

**排障顺序**（经验）：

| 日志停在 | 问题所在 |
|---|---|
| 第 1 步无 401 | `challenge-enabled` 未开启，或传输不是 Streamable HTTP |
| 第 2 步无请求 | 客户端未消费 401 / 配置未重载 |
| 第 4 步 400 | 动态注册响应未回显 `redirect_uris` |
| 第 7 步之后无 `/token` | 浏览器回调未真正到达客户端（回调地址不匹配） |
| 第 7 步 400 `invalid_grant` | 授权码重复消费 / PKCE 不匹配 / `redirect_uri` 不一致 |

## 八、已修复缺陷与踩坑记录

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 端口不是 3100 | IDE 注入 `SERVER__PORT`，环境变量优先级高于 yml | 启动类以命令行参数注入端口 |
| 2 | SSE 握手请求抓不到 | 记录放在 `finally`，长连接不结束就不记录 | 改为请求进入时立即记录 |
| 3 | `POST /mcp/message` 无响应 | SSE 长连接占满 Tomcat 线程 | `threads.max: 200` |
| 4 | 调用工具一直挂起 | 跳过 MCP `initialize` 直接调 `tools/list` | 补全握手顺序 |
| 5 | 启动失败（bean 冲突） | 自定义 `RequestContextFilter` 与 Spring MVC 内置同名 | 改名 `CallerContextFilter` |
| 6 | 验签通过但 `claimsVerified=false` | 过滤器写入 `UsernamePasswordAuthenticationToken`，解析器判定 `JwtAuthenticationToken` | 改为写入 `JwtAuthenticationToken` |
| 7 | 401 挑战不触发 OAuth 发现 | 使用了 SSE 传输 | 改用 Streamable HTTP |
| 8 | 元数据 404 | 路径未带资源后缀（RFC 9728 §3.1） | 同时提供带/不带后缀两条路径 |
| 9 | `/oauth/authorize` 返回 406 | `produces = TEXT_HTML_VALUE` 与客户端 `Accept` 不匹配 | 去掉 `produces` 限制 |
| 10 | 本地 curl 访问失败 | `http_proxy` 环境变量 | 加 `--noproxy '*'` |

## 九、生产化改造清单

### 必须改造

| 项 | 当前 | 应改为 |
|---|---|---|
| 授权服务器 | 内置 `embedded: true` | `false` + 企业 SSO |
| 演示账号 | `demo-users` 有 3 个 | **删除** |
| 观测端点 | `/__capture/**` 免登录 | 移除或加认证 |
| 身份来源 | 信任 header 候选列表 | **只信任已验签 JWT**，清空 header 候选 |
| 传输加密 | HTTP（本地） | **HTTPS**（远程 MCP 强制） |
| OAuth 状态 | 内存 | Redis / DB（多实例部署） |

### 建议加固

- **限流**：`/oauth/register`、`/oauth/authorize`、`/oauth/token` 分别限流
- **TTL 与容量**：动态客户端、授权码、pending 请求都要有上限，防止内存增长
- **日志脱敏**：token / 授权码 / 密码不得落日志
- **幂等**：登录按钮重复提交需服务端幂等（同一 `request_id` 只允许一个请求执行）
- **审计**：记录每次工具调用的 `userId` / 时间 / 参数摘要

### 安全边界（重要）

> **OAuth 解决「你是谁」，不解决「你能看什么」。**
>
> 业务数据的按人过滤必须由**业务系统**完成，不能只依赖 MCP 层。
> 必须做交叉越权测试：A 只能查 A 的数据，A 查 B 的对象应返回 404/403。
